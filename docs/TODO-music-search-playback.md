## 1. 目标

在应用内搜索自己的音乐库并直接播放。

核心难点不是 UI，而是**搜索来源** —— WebDAV 协议本身没有服务端搜索能力，
所以「可搜索的数据从哪来」决定了整个方案的形态。

---

## 2. 搜索来源的方案选择

### 已定：应用内后台扫描

用户主动触发，后台递归扫描整台服务器，把结果落到本地，供搜索使用。

**为什么不用 OpenList 原生搜索**（虽然它更省）：

服务器上跑的 OpenList（v4.2.5）自带搜索索引，接口 `POST /api/fs/search`
一次请求即可返回全部匹配（`scope` 支持递归）。但：

| | 应用内扫描（已选） | OpenList 原生搜索 |
|---|---|---|
| 请求量 | 几百 ~ 几千次 | 1 次 |
| 通用性 | ✅ 任意 WebDAV 服务器 | ❌ 仅 OpenList |
| 服务端准备 | 无 | 需启用并构建索引 |
| App 需持有的凭据 | WebDAV 应用密码 | OpenList 账号密码（权限更大） |

实测服务器当前状态：`search_index: none`（未配置索引），且
`/api/fs/search` 未认证返回 `{"code":401,"message":"Guest user is disabled"}`。

考虑到后续**计划上架供他人使用**，通用性优先，因此选择应用内扫描。
OpenList 原生搜索可作为**后续针对 OpenList 用户的加速项**，不在本次范围。

## 3. 已确认的决策

| # | 项 | 决定 |
|---|---|---|
| 1 | 并发数 | **3** |
| 2 | 扫描范围 | **整台服务器**（从当前服务器的 `/` 递归） |
| 3 | 硬上限 | **4000 个目录 / 10 分钟**（先到者中止） |
| 4 | 结果展示 | **目录数 + 歌曲数** |
| 5 | 执行方式 | **后台执行**；完成后弹窗提示；扫描中再次点击给出提示；完成后点击 = 全部重新扫描 |
| 6 | 清空缓存 | 清空前提示「将同时清除音乐库索引」 |

## 4. 可行性核算（基于真机实测）

真机日志（Xiaomi 24031PN0DC / Android 15）实测数据：

- 单目录 PROPFIND 耗时：**约 188ms**（AI工具箱那次：清空列表 → 结果返回）
- 已访问过 30 个不同目录，单目录最多 206 条

| 项 | 值 |
|---|---|
| 上限要求速率 | 4000 目录 / 600 秒 = **6.67 目录/秒** |
| 并发 3 下允许的单请求耗时 | **≤ 450ms** |
| 理论总耗时（188ms/请求） | 4000 × 0.188 / 3 ≈ **250 秒** |

**结论：4000 目录 / 10 分钟可行，余量约 2.4 倍。**

⚠️ 两个上限是「先到者中止」。网络差时会是**时间先到**、目录没扫完，
此时结果弹窗必须如实说明（例：「因超时中止，已扫 2870 个目录」）。

## 5. 设计

### 5.1 存储：复用现有目录快照 + 新增扁平索引

**① 复用目录快照**（已有机制，`LocalCacheManager.saveSnapshot`）

扫描的本质就是「逐个目录 PROPFIND 并把结果写成快照」，因此直接复用：

- 无需新格式、新迁移
- **扫完再浏览 = 零请求**（所有目录快照已预热）
- 位置：`getFilesDir()/snapshots/`（**持久目录，非 cacheDir**）
  - 注：v1.31 之前确实在 `cacheDir`，已迁移到 `filesDir` 并做了数据搬迁

**② 新增扁平索引**（搜索专用）

只有目录快照的话，搜索要遍历 4000 个 JSON 文件，太慢。扫描时额外写一份：

```
filesDir/library_index.json
{
  "serverId": "...",
  "serverName": "cmcc",
  "scannedAt": 1789...,
  "dirCount": 4000,
  "songCount": 12000,
  "truncated": false,        // 是否因上限中止
  "songs": [
    {"n": "歌名.m4a", "p": "cmcc/music/...", "s": 12345}
  ]
}
```

12000 首 × 约 150 字节 ≈ 1.8MB，读一次进内存即可即时搜索。

### 5.2 扫描流程

```
用户点击「扫描音乐库」
  → 已在扫描中？→ 按 §7 决策 (a)/(b) 处理
  → 启动 ScanService（前台服务）
  → 递归遍历：并发 3，visited 集合去重，逐目录 PROPFIND
      · 每个目录成功 → 写目录快照 + 累积索引条目
      · 单目录失败 → 跳过继续，累计失败超阈值则中止
      · 遇 429 → 【立即中止整个扫描】+ 弹提示，不重试
      · 达到 4000 目录或 600 秒 → 中止并标记 truncated
  → 写 library_index.json
  → 通知栏更新 → 完成后弹窗显示「目录数 + 歌曲数」
```

### 5.3 关键设计约束

| 项 | 处理 | 原因 |
|---|---|---|
| **遇 429** | 立即中止整个扫描，弹提示 | AGENTS.md §3 原文要求；曾有客户端把 OpenList 打到封禁的真实事故 |
| **不写内存缓存** | 扫描只写磁盘快照 | 4000 × 200 条目 ≈ 80MB，会导致 OOM |
| **进度反馈** | 前台服务常驻通知显示 `1234/4000` | 10 分钟无反馈，用户无法区分「在跑」和「卡死」 |
| **可中断** | 通知栏提供停止入口 | 否则用户被绑架 10 分钟 |
| **快照原子写** | 先写 `.tmp` 再 rename | 见 §5.4 |
| **重复目录** | visited 集合去重 | 避免重复请求 |
| **多服务器** | v1 只扫当前服务器 | 按「当前目录服务器」的定义 |
| **在服务器列表时** | 提示「请先进入某个服务器」 | 此时无 `currentServer` |
| **扫描中途被杀** | 状态存 SharedPreferences；已写快照保留 | 增量天然可恢复，重启后标记「已中断」 |

### 5.4 必须先修的前置问题：快照写入非原子

当前实现（`LocalCacheManager:306`）：

```java
try (FileOutputStream fos = new FileOutputStream(snapshotFile)) {
    fos.write(snapshotJson.getBytes());     // ← 非原子
}
```

平时浏览一次只写一份，风险低。但**扫描会在 10 分钟内写 4000 份**，
窗口被放大几千倍：中途被杀/断电可能留下半截 JSON。
`loadSnapshot` 会捕获异常返回 null（降级为「无快照」，不崩溃），
但等于白扫一个目录。

**改成「先写 `.tmp` 再 rename」即可消除。**

### 为什么加前台服务与权限

「后台执行」在 Android 上必须用前台服务，否则切后台会被系统冻结、
扫描中断。需新权限 `FOREGROUND_SERVICE_DATA_SYNC`（normal 级，
无需运行时申请）与新服务，与 `MusicService`（`mediaPlayback`）并存
—— Android 允许两个前台服务各自持一个通知。

这违反「不加复杂度」的默认倾向，但 10 分钟的后台任务没有别的合规做法
（AGENTS.md 已明确否掉 WorkManager）。

## 7. ⚠️ 未决事项（动手前需确认）

### 7.1 「扫描中再次点击」的语义

需求原文是「扫描中再次点击扫描弹 toast 提示扫描停止」，有两种读法：

- **(a) 只提示**：弹「扫描正在进行中」，不重复启动，扫描继续跑
- **(b) 点击即停止**：toggle 行为

**倾向 (b)**，理由：10 分钟的扫描若用户想中断却没有出口，体验很差；
且与「扫描完成后点击 = 全部重新扫描」构成一致的 toggle 语义。

若选 (a)，仍建议**额外提供取消入口**（通知栏的「停止」按钮），
否则用户只能等满 10 分钟。

### 7.2 前台服务与新权限

需确认同意新增 `FOREGROUND_SERVICE_DATA_SYNC` 权限与一个前台服务
（理由见 §6）。这是本方案里唯一显著增加复杂度的部分。
